Where we were

The starting point

Before this PR, the harness package had its passive pieces in place: events.py (the typed event protocol from T-02), state.py (AgentState from T-03), and the model adapter base classes. What was missing was the active piece — the thing that actually turns the crank: model call → tool calls → tool results → back to the model, until the model says it's done.

T-05 fills that gap with three things: an async generator loop, a public Harness + Session facade, and the two minimum support modules the loop needs to work today (cache.py, truncation.py) as honest stubs.

Why now: nothing else can be built end-to-end without a loop. Tools (T-07), guardrails (T-06/T-08), CLI (later), and eval all need something to drive them. T-05 is the smallest thing that unblocks all of them while preserving SPEC §5.3's "intentionally legible" constraint.

Architecture

The shape of the loop

SPEC §5.3 says the loop should be ~300 lines of straight-line code that a reader can take in at a sitting. The implementation is one async generator function with three explicit numbered suppressions for ruff (C901, PLR0912, PLR0915) and a comment that says, in effect, "yes, on purpose."

┌──────────────────────────────────────┐ │ Session.run_stream(query) │ │ appends user Turn, calls run_loop │ └──────────────┬───────────────────────┘ ▼ ┌────────────────────────────────────────┐ │ run_loop(state) │ │ │ ┌──────────┤ while not state.done: │ │ │ state.refresh_context() (G6/G7) │ │ │ state.context_pressure() (G5/G10) │ │ │ prompt = state.build_prompt() (G1) │ │ │ action = await adapter.call(prompt) │ │ │ │ │ │ ┌─ final_answer? ─► FinalAnswerEvt │ │ │ ├─ no progress? ─► FinalAnswerEvt │ │ │ └─ tool_calls ─► dispatch ──┐ │ │ │ │ │ │ │ for tc in action.tool_calls: │ │ │ │ if pseudo → _dispatch_pseudo │ │ │ │ else → queue real │ │ │ │ │ │ │ │ flush real batch: │ │ │ │ parallel? gather : serial │ G11│ │ │ ↳ cache check (G9) │ │ │ │ ↳ tool.run(args) │ │ │ │ ↳ truncate_for_tool (G2) │ │ │ │ ↳ emit ToolResultEvent │ │ │ │ │ │ │ │ state.iterations += 1 │ │ │ │ guard: max_iters / max_errors │ │ └──────────┘ │ │ └─────────────── yield Event ◄──────┘ │ │ caller iterates → stops when iterator │ completes; cancellation = stop the loop. ┘
Why a generator and not a callback registry: every yield is a checkpoint. The caller controls cadence; the loop owns no background tasks. Cancelling the iterator cancels the loop cleanly — there is nothing to clean up because there is nothing in flight that isn't tied to the current await.
Tradeoff accepted: the function is long. Splitting it into _handle_final(), _handle_calls(), etc. would shrink each piece but hide the control flow behind helper names. SPEC §5.3 explicitly chooses readability over decomposition here.
Public API

Harness vs. Session — the two-layer split

The public surface is two objects with a sharp responsibility line.

HarnessSession
LifetimeBuilt once, reusedOne conversation
MutabilityImmutable (frozen-ish dataclass)Mutable; mutates AgentState
OwnsAdapter, tool list, role, budget knobsAgentState, ToolResultCache, event log
Spawnssession() → Sessionfork() → Session

Session.run_stream(query) is the streaming entry point; Session.run(query) is a one-line consumer that drains the stream and returns the FinalAnswerEvent. Same loop under both — no duplication.

Per-query iteration budget

Inside run_loop, the very first thing that happens is state.iterations = 0. That makes max_iterations a per-query budget, not a per-session one.

Why: a long-lived session can hold dozens of turns. If the budget were cumulative, a healthy session would hit the wall mid-way through a perfectly normal conversation. Per-query is the unit users actually reason about ("don't loop more than 25 times on this question").

Forking

Session.fork(at_turn=-1) returns a new Session with a fresh cache and event log, parent_id pointing back. This is the foundation T-23 needs for A/B/C comparison of REIGNER.md / tool / model variants without re-running from scratch (SPEC §11).

Guardrail G9

The tool-result cache

harness/cache.py Every Session owns one ToolResultCache. The loop consults it only for tools whose readonly flag is true, keyed on (tool_name, args): 

@staticmethod
def _key(tool_name: str, args: dict[str, Any]) -> str:
    return f"{tool_name}:{json.dumps(args, sort_keys=True,
                                     separators=(',', ':'),
                                     default=str)}"
Why sort_keys=True: the model may issue the same logical call with arg keys in different orders. Sorted JSON + tight separators give a deterministic string key so {"path":"a","offset":0} and {"offset":0,"path":"a"} hit the same entry. Verified by test_args_order_independent.

Cache stores untruncated results

Important detail: the cache stores the raw tool result and truncation runs on the way out. A model that gets a result twice — once fresh, once cached — sees the same shape both times.

Errors are not memoized

_execute_one only writes to the cache on success. A transient failure shouldn't poison subsequent calls.

Guardrail G2

Bounded outputs

harness/truncation.py PRINCIPLES §3 says: when we truncate, the returned shape must say so explicitly so the model can ask for more. The stub honors that with a JSON-aware, char-budget truncator.

Result typeStrategyMarker added
strHard slice with trailing suffix"... [truncated]"
listLongest prefix that fits, wrapped in dict_truncated, _original_count
dictLargest insertion-order prefix that fits_truncated, _original_keys
otherStringify + slice_truncated, _value

The bug worth calling out

First implementation of the list/dict branches checked the candidate size without the marker fields, then added them at return time. The result overshot the limit. Fix: include _original_count / _original_keys in the candidate dict the loop measures against. 

if isinstance(result, list):
    kept: list[Any] = []
    for item in result:
        candidate = {
            "items": [*kept, item],
            "_truncated": True,
            "_original_count": len(result),  # <-- counted in the budget
        }
        if _serialized_size(candidate) > char_limit:
            break
        kept.append(item)
    return {"items": kept, "_truncated": True,
            "_original_count": len(result)}, True
Why JSON-serialized size: the budget is "what goes into model context." That's the JSON form, not len(repr(value)).
Local control plane

Pseudo-tools — dispatched inline, never to the wire

Four tool names are intercepted by the loop itself and never reach an external service:

save_note request_clarification stop escalate_to_oracle

They live in a single frozenset at the top of loop.py and dispatch through one _dispatch_pseudo function with one branch per name. SPEC §6.4 explicitly wants this not behind a plugin registry — a reader of the loop should see every special case in one place.

Guardrail G11

Parallel reads — without breaking event order

When every real call this turn is readonly=True, the loop runs them concurrently with asyncio.gather. But emission order has to stay deterministic so callers (CLI, MCP) see the same stream every time.

The trick is two-phase emission inside _run_real_calls:

# Phase 1: emit ALL ToolCallEvents in original order (no awaits).
for tc in calls:
    yield ToolCallEvent(...)

# Phase 2: gather concurrently, but await once before any results stream.
if parallel and len(calls) > 1:
    results = await asyncio.gather(
        *(_execute_one(tc, ...) for tc in calls)
    )
else:
    results = [await _execute_one(tc, ...) for tc in calls]

# Phase 3: emit results in the same order calls were issued.
for tc, (raw, cache_hit, errored) in zip(calls, results, strict=True):
    yield ToolResultEvent(...)
Why this order: the model issued calls in a specific order; the event stream should reflect that. Parallel execution is an optimization, not a reordering primitive — observers should never see a result before its call.

Mixed pseudo + real batches

If a turn includes both pseudo and real tool calls, the loop walks them in the order the model issued them. When it hits a pseudo-tool, it first flushes any queued real calls so emission stays stable. Some pseudo-tools are terminal (stop, request_clarification) — when one fires, terminate_after_calls is set and any remaining queued real calls are dropped (the model already decided to end).

Out of scope, on purpose

What was deliberately deferred

Five things you'll find as NotImplementedError stubs:

  • Harness.from_config(path) → waits on the reigner.yaml loader (T-26).
  • Session.steer(message, mode) → signature in place; wiring lands with T-06.
  • Session.save() / Session.load() → wait on the JSONL session store (T-23).
  • Profile filtering ("read_only", "eval") → needs the tool registry (T-07); only "full" works today.
  • Real oracle execution inside escalate_to_oracle → emits event, executes no-op.

Each stub has the public signature in place so consumers (later tasks, eval scripts, CLI) can already type-check against the final shape.

For the reviewer

Reviewer's checklist

If you're reviewing this branch, the highest-leverage things to verify:

  • Read loop.py top-to-bottom in one sitting — that's the test of SPEC §5.3's "stays legible." If it doesn't, that's a finding.
  • Check that the guardrail comments at the top of loop.py match the actual hook points in the body.
  • Confirm event seq numbers are monotonic across the streaming + run-and-collect paths (seq_start=len(self._events) in agent.py).
  • Sanity-check the two-phase emission in _run_real_calls — calls all yielded before any await, results yielded in original order after gather.
  • Make sure no production path raises out of a tool. Tool exceptions become {"error": "..."} dicts the model can react to (_execute_one).
  • Verify Session.fork creates an independent cache + event log — sessions sharing a cache would silently leak across A/B comparisons.
  • Check the NotImplementedError stubs: the messages name the task that will land them, so future-readers know where to look.
Mental model to carry into the review: this PR is deliberately the thinnest loop that can run a real model end-to-end without violating any of the 11 guardrail contracts. Where a guardrail isn't fully implemented, the loop either delegates to an existing module (G1/G6/G7) or bails honestly (G3/G4) rather than faking it.
